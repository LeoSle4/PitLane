## Specs

- S1 Unique DNI: "DNI único con reserva". A reservation collection `dnis/{dni}` = { usuarioId } is written in the same batch or transaction as the user profile, exactly like `placas/{placa}`. It applies to the Jefe registering a client without an account (app), and to the Cloud Functions `registrarCliente` (linking a previous profile keeps its reservation) and `crearTecnico`. The rules make a profile with a DNI impossible without its reservation, and a reservation impossible without its profile. A backfill script (dry run by default) creates the reservations for existing users and reports duplicates without touching them.
- S2 Notifications as a subcollection: "Notificaciones en subcolección". `notificaciones/{id}` becomes `usuarios/{usuarioId}/notificaciones/{id}`. `notificarOrden` writes there; the app reads and marks as read under the user's path; the rules authorize by path. The TTL policy is per collection group, so the name `notificaciones` stays. A backfill script (dry run by default) moves the existing ones.
- S3 Advances as a subcollection: "Avances en subcolección". `avances/{id}` with `ordenId` becomes `ordenes/{ordenId}/avances/{id}`. Reading an order's advances is a subcollection read; a technician's own advances (if any screen lists them) use a collection-group query. The rules authorize from the parent order. A backfill script (dry run by default) moves the existing ones. Indexes are updated.
- S4 Dates the client cannot fake: "Fechas con serverTimestamp". Decision (see L2): keep `Long` milliseconds and require in the rules that every top-level date written by the app (`ordenes.creadaEn`, `editadaEn`, `solicitudes.creadaEn`, avance `fechaHora`) and the new history entry's `fechaHora` be within a tolerance of `request.time`. This also covers the history array, where serverTimestamp is not allowed.
- S5 Diagrams: "las necesarias, y has un buen analisis de los diagramas, para la idea es que el ER sirva como explicaicon de la conexion de documentos, pero el diagrama de clases ya tiene que mostrar como es la base de datos en no sql, con todo lo necesario". The ER explains how the documents connect; the class diagram shows the NoSQL database exactly as it is: collections, subcollections, embedded documents, references, reservations and support collections, with every field.

- `placas/{placa}` (commit d563e5e, 2026-10-31) is the correct Firestore pattern: the document id is the only uniqueness guarantee.
