L2 (analysis):
- ER: CAMBIO DE ESTADO, CONFORMIDAD and OBSERVACIÓN were drawn as weak entities with only dates and text and no relationships of their own. That is the textbook signal for attributes of a relationship. Proposed: a new ESTADO entity (catalog) plus a ternary relationship "cambia de estado" ORDEN–ESTADO–USUARIO with {fecha y hora, motivo}. That relationship IS the history. "da conformidad" CLIENTE–ORDEN (1:1) with {fecha y hora}; "observa" CLIENTE–ORDEN (N:M) with {fecha y hora, texto, acuerdo}; "ingresa en" VEHÍCULO–ORDEN with {fecha de ingreso, kilometraje, combustible}, which describe the vehicle at the moment it entered. AVANCE stays a weak entity because it has its own multivalued attribute (fotos) and its own author.
- Logical: the detail tables are what the ER produces once normalized: HistorialEstado (from the ternary relationship), ObservacionCliente (N:M), Conformidad (1:1 detail), FotoOrden, FotoSolicitud, FotoAvance and SintomaSolicitud (multivalued attributes), plus the catalog EstadoOrden. Snapshots, `acceso`, `terminos`, `esquema` and `expiraEn` are physical concerns and leave the logical diagram.
- Physical: in Firestore the detail table HistorialEstado is the embedded array `ordenes/{id}.historial`; `estado` is the derived "current state" copied from its last entry. Each state change is one atomic update that appends an entry and sets `estado`, and two triggers react to it (notificarOrden, actividadPorOrden).
- Gap found: the rules let the technician (and the Jefe) send `historial` as a whole new array, so past entries could be rewritten or signed as someone else. Proposed improvement S4.

L3 (T4 evidence): RED 4 of 6 new tests failed against the previous rules. Six existing order tests changed `estado` without appending an entry (they encoded the gap) and now append it. A date-ordering check was dropped: Firestore forbids serverTimestamp inside arrays, so the date comes from the device, and a phone clock behind the Jefe's would block legitimate work. Found before deploying: entries written before 84b78c7 lack `usuarioNombre`, and the mapper re-sends it as null (missing != null), so those orders would be locked. Fix: `functions/scripts/rellenarHistorial.mjs` (dry run by default, not run against production) plus a pure normalizer with unit tests, documented in firebase/README.md as a step before the rules.
L4 (T4 independent verifier): every real app write path passes HEAD and NEW rules with the same result; all bypasses (rewrite, prepend, two entries, sign as another user, change state without entry) are now denied. BLOCKER: `motivo`/`usuarioNombre` were not type-checked; a non-string value would lock the order once the app re-sent it as null. Fixed with type and length checks plus a regression test. Notes kept: `usuarioNombre` can be any string (UI fallback only) and `fechaHora` any int (documented limitation); an APK older than 84b78c7 would be blocked after the backfill; a stored `historial: null` would deny edits (the app never writes it).
L5 (layout): DISPOSITIVO and NOTIFICACIÓN left the conceptual model (technology and system-derived effects). That allows an orthogonal layout with no crossings, and both remain in the logical and physical models. Old Graphviz sources were moved to `anterior/` folders (docs/ is not in git).
